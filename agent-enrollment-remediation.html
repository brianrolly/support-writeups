Case 04 · Security Support and Access Control

Closing an Unauthenticated Enrollment Path

An authorized validation showed that a reachable host could obtain a trusted monitoring identity without presenting a credential. The root setting was corrected, the unauthorized identity was removed, and the same request was rejected on retest.

Primary exposure fixed WazuhTLSAccess controlIncident cleanup

Finding

The service issued trust before proving identity

The monitoring platform’s enrollment service was reachable and configured with password enforcement disabled. During an authorized test, a raw TLS enrollment request returned a valid agent key without a challenge.

That key allowed the test host to become an active, trusted telemetry source. It then generated a fabricated authentication event that appeared in the central alert stream as if it came from a monitored system.

Selected excerpts from the August 20–21 exercise record show the path. The manager address and issued key are redacted; these checks came from different hosts and are not a continuous terminal transcript.

1515/tcp open   agent enrollment
<use_password>no</use_password>
wazuh-authd: Accepting connections on port 1515. No password required.

From the authorized test host, a raw TLS request returned a manager-issued identity without a credential:

echo "OSSEC A:'ROGUE-TEST-DELETEME'" | openssl s_client -connect [manager]:1515 -quiet
OSSEC K:'002 ROGUE-TEST-DELETEME any [key redacted]'

A second issued identity, agent 003, became active in manager inventory:

/var/ossec/bin/agent_control -l
ID: 003, Name: ROGUE-TEST-2, IP: any, Active

This test command and selected fields from the preserved alert export show what that identity could send:

logger -t sshd "Failed password for invalid user PURPLEINJECT from 203.0.113.66 port 4444 ssh2"

Exported alert, 2026-08-21 00:27:06 UTC
agent.id:       003
agent.name:     ROGUE-TEST-2
rule.id/level:  5710 / 5
data.srcuser:   PURPLEINJECT
data.srcip:     203.0.113.66

The source address in that alert is documentation-only space. The sanitized 35-row alert comparison contains 34 genuine SSH alerts and the fabricated row E27 under the same agent identity and rule. The forged row still had detectable field and session-shape differences; the test proved alert forgery, not an indistinguishable copy.

Containment and evidence

Stop the source without losing the record of what happened

The test agent was stopped and removed. The recorded cleanup used manage_agents -r 002 and manage_agents -r 003; manager inventory then showed only the authorized agent. After a sanitized evidence export was retained, an administrator removed 363 records attributed to agent 003 from the active index. That index deletion required separate manager-level access; the issued agent key did not grant it.

The manager’s ossec.log and API api.log were added to central collection so later enrollment, configuration posture, and authentication activity could be investigated from the monitoring platform itself.

Key distinction: removing the agent stopped additional injection, but it did not correct the configuration that issued the identity. Containment and remediation were separate tasks.

Root-cause remediation

Require a shared secret for enrollment

Password-protected enrollment was enabled, and the required secret file was configured on the manager. The enrollment port continued listening because legitimate agents still needed it, but possession of network access alone was no longer sufficient.

Sanitized configuration comparison; the secret value is withheld:

before: <use_password>no</use_password>
after:  <use_password>yes</use_password>
        authd.pass configured
        TCP/1515 still listening

Validation

Repeat the same request against the corrected system

On August 21, the same unauthenticated request was repeated against the changed manager configuration. The recorded response was:

echo "OSSEC A:'ROGUE-TEST-DELETEME'" | openssl s_client -connect [manager]:1515 -quiet
ERROR: Invalid password. Unable to add agent
✓
The manager rejected the original request without a password while TCP/1515 remained available for legitimate enrollment.
✓
The two test identities were no longer present in manager inventory after cleanup.

Separate live detection re-runs during the exercise fired enrollment rule 100361. Nineteen API authentication failures (built-in rule 411) triggered aggregate rule 100360 and a 600-second firewall-drop. Agent-removal rule 100363 passed wazuh-logtest; a live removal positive control was still outstanding.

Remaining work

The primary flaw was closed, but the management plane still needed hardening

Password-gated enrollment was verified. Related follow-ups remained for API network exposure, host firewall policy, and visibility into privileged bulk deletion. This case is therefore labeled “primary exposure fixed,” not fully closed.
