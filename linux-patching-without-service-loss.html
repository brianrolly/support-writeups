Case 03 · Linux Systems Support

Patching Linux Without Breaking the Stack

Two hosts were behind on kernels and security packages. The change had to preserve version-sensitive monitoring components and custom configuration, then restore services and the end-to-end telemetry path after planned reboots.

Validated on two hosts UbuntuAPTProxmoxNGINX

Risk

A clean reboot would not be enough

The hosts included a central monitoring server and a Linux endpoint with audit rules, a web service, and an active agent. Routine operating-system patching could unintentionally upgrade version-sensitive platform packages or overwrite custom configuration.

The acceptance condition was therefore larger than “the machine came back.” Services, listeners, agents, audit rules, web response, and the complete telemetry path all had to remain functional.

Preparation

Capture a rollback and a meaningful before-state

  • Create snapshot-mode VM backups before maintenance.
  • Record the running kernel, installed kernels, and reboot-required state.
  • Record the active services and network listeners appropriate to each host.
  • Confirm the endpoint’s audit-rule count and web-service response.
  • Hold platform packages that require an ordered, separate upgrade window.
manager host: services + listeners + established log session
endpoint:     agent + auditd + nginx + audit rule count
both hosts:   kernel + pending reboot + package holds

Change control

Simulate the upgrade before applying it

The package manager’s full-upgrade plan was reviewed for removals, version-sensitive packages, and new dependencies. This caught whether the holds were working before the live transaction.

The upgrade preserved existing configuration files where packages supplied new defaults. Each host was rebooted only after its package transaction completed and the pre-state was recorded.

Operational guardrail: after the SSH session closed for reboot, post-change verification started by checking the hostname. That prevented healthy results from being collected accidentally from the administrator’s local machine.

Validation

Verify the components, then prove the workflow

✓
Both systems booted the intended current kernel, and the reboot-required flag cleared.
✓
Monitoring, indexing, dashboard, shipping, and endpoint services returned active.
✓
Network listeners and the established remote logging session returned.
✓
The endpoint retained 26 audit rules, and NGINX returned the expected local HTTP response.
✓
A fresh functional test produced the expected security event at the destination.

The August 8 maintenance record and follow-up handoff support this condensed verification summary; it is not a verbatim terminal transcript.

Before maintenance: both hosts running stale kernels
After planned reboot: both on kernel 6.8.0-138
                      reboot-required flag clear
                      endpoint audit rules retained: 26
                      fresh detection confirmed at destination

Both hosts moved from stale kernels to current packages. The planned reboots interrupted service, but post-maintenance checks found no unexpected service failures. The monitoring server’s Lynis hardening index progressed from 55 to 68 across the broader hardening and patching work.

Scope boundary

Routine OS maintenance stayed separate from platform upgrades

Central monitoring components were intentionally held. Their required upgrade order and compatibility constraints made them inappropriate for a routine full upgrade. They remained a separate maintenance task with its own backup, validation, and recovery plan.

What this demonstrates

  • Linux patch and reboot ownership
  • Package simulation and dependency holds
  • Proxmox snapshot backups
  • systemd, listeners, and process checks
  • NGINX and auditd validation
  • Runbook-driven change management
