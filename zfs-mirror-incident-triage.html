Case 05 · Infrastructure Escalation

Diagnosing a Degraded ZFS Mirror Safely

A virtualization host was still running, but one member of its NVMe mirror had failed at the controller level. The priority was to identify the exact device, verify the surviving path, expose the recovery risk, and avoid turning degraded redundancy into an outage.

Open escalation ProxmoxZFSNVMeRecovery planning

Status: this case documents completed diagnosis and escalation, not a completed disk replacement. Physical maintenance and pool modification required separate authorization.

Situation

Healthy applications were masking a critical redundancy failure

The virtualization host remained online and its pool reported no known data errors, but the ZFS mirror was degraded. One NVMe namespace reported zero bytes, and the system was operating entirely from the surviving member.

A quick pool clear or online command would have treated the status rather than the hardware failure. All initial work was therefore read-only.

Evidence

Trace the failure from the kernel to the physical slot

The investigation used read-only commands and stable identifiers. The excerpts below are from the incident transcript collected on September 4, 2026. Hostnames, full serial numbers, and full EUI values are shortened; device states, sizes, counters, and error messages are unchanged.

1. Confirm the pool state before touching a device

zpool status established that the pool was still serving data from one member, the peer had been removed, and ZFS had not reported data corruption.

2. Compare the two namespaces at the block-device layer

The failed controller still appeared in inventory, but its namespace reported 0 B. The surviving namespace exposed the expected 1.8 TiB capacity and partition layout.

3. Reconstruct the failure sequence from the kernel

The kernel log ruled out a stale ZFS status. Multiple writes timed out, the reset failed, Linux disabled the controller, and ZFS then recorded I/O errors against the same stable member.

4. Correlate the logical member to a stable hardware path

udevadm linked the failed member’s EUI and serial suffix to PCI address 0000:09:00.0. The healthy member resolved to 0000:0c:00.0. Board documentation then mapped those paths to the chipset-connected M2_2 slot and CPU-connected M2_1 slot respectively.

ID_WWN=eui.…ed45

Survivor validation

Verify both data health and the remaining boot path

A healthy pool member was necessary but not sufficient. The remaining NVMe device also had to pass its own health checks, and the host needed a working EFI System Partition on that same disk.

root@proxmox-lab:~# smartctl -x /dev/nvme1 | \
  grep -E -e 'assessment|Temperature:|Available Spare:|Percentage Used:' \
  -e 'Media and Data|Error Information Log'
SMART overall-health self-assessment test result: PASSED
Temperature:                        33 Celsius
Available Spare:                    100%
Percentage Used:                    4%
Media and Data Integrity Errors:    0
Error Information Log Entries:      0

root@proxmox-lab:~# proxmox-boot-tool status
System currently booted with uefi
3C36-9255 is configured with: uefi (current kernels present)
mount of /dev/disk/by-uuid/3C3E-4FC4 failed - skipping

This did not prove the surviving SSD could never fail. It established the narrower facts required for a safe handoff: the readable member had no recorded media errors, the host was currently bootable from its EFI partition, and the failed member’s EFI partition was also unreadable.

Risk discovery

The configured backups shared the failed storage domain

The only scheduled archives were stored on local storage backed by the same degraded pool. That meant they were convenient restore points, but not independent recovery copies.

A guest named for backups also resided on the same pool. Without proof of external replication, its presence could not be counted as off-host protection.

root@proxmox-lab:~# pvesh get /cluster/backup --output-format json-pretty
[
  {
    "mode": "snapshot",
    "storage": "local",
    "prune-backups": { "keep-last": "3" },
    "vmid": "<two selected guests>"
  }
]

root@proxmox-lab:~# pvesm status
Name       Type     Status
local      dir      active
local-zfs  zfspool  active

# Storage mapping confirmed both targets were backed by rpool.

Recovery gate: verify and copy critical data to an independent destination before powering down, reseating hardware, or modifying the pool.

Evidence-based decisions

Each observation changed the next action

1
DEGRADED plus REMOVED: stop treating the incident as a cosmetic alert and avoid new storage load.
2
Zero-byte namespace plus failed controller reset: do not use zpool clear or zpool online as a substitute for physical repair.
3
Stable EUI, serial, and PCI mapping: give the physical operator an unambiguous failed-slot warning that protects the surviving disk.
4
Healthy SMART and EFI evidence: document the current survival path without overstating long-term reliability.
5
Backups on the same pool: require an independently stored, checksum-verified copy before maintenance.

Escalation plan

Make the physical action unambiguous

The recovery plan identified the failed slot and serial number, distinguished it from the healthy member, and required console access, a maintenance window, and a verified replacement device before intervention.

  1. Verify off-host backups and checksums.
  2. Export virtualization configuration and guest definitions.
  3. Power down cleanly for physical service.
  4. Identify the replacement by model, serial, capacity, and stable device path.
  5. Replicate the healthy partition layout to the confirmed replacement.
  6. Replace the missing ZFS member and initialize the replacement EFI partition.
  7. Wait for resilver completion and require the pool to return online.
  8. Scrub the pool, verify zero data errors, and confirm both boot partitions.

Outcome

A safe diagnosis and handoff, not an invented resolution

The exact hardware failure, surviving boot path, current integrity state, backup weakness, and recovery sequence were documented. No disk was detached, no partition table was copied, and no pool replacement command was run without the required authority.

For escalation support, knowing when not to make a technically possible change is part of owning the incident.
