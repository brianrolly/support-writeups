Case 01 · Linux and Application Support

Recovering a Capacity-Limited Search Platform

A seven-day aggregation failed with a circuit-breaker error that initially looked like a client-side parsing problem. The real cause was a severely undersized JVM heap on an otherwise healthy host.

Fixed and verified OpenSearchJVMsystemdCapacity

Situation

A query failed while the platform looked healthy

A routine seven-day measurement was run against a single-node search and monitoring platform. One daily slice worked, but the remaining slices failed. Because the response was piped directly into a JSON processor, the first visible message was “cannot iterate over null.” That looked like a client-side data problem.

Reading the raw response exposed the actual failure: the search service had rejected the request because its parent circuit breaker was already near the configured heap limit.

circuit_breaking_exception
data for request would be approximately 974 MB
configured parent limit was approximately 973 MB

Investigation

The request was small. The standing overhead was not.

Configured heap1 GB
Host memory12 GB, about 9 GB available
Shard count540

The breaker report showed almost no request or field-data allocation. The query itself was not consuming the missing memory. The node was sitting at roughly 83 percent heap usage before it received the request.

Old-generation garbage collection had not run in the observed period, providing no evidence of repeated full-collection thrashing. The breaker and heap measurements pointed to too little configured heap for the steady shard overhead.

Root cause: a 1 GB JVM heap had been left on a 12 GB host. Standing per-shard overhead consumed most of it, leaving too little room for multi-day aggregations.

Change

Increase capacity without starving the rest of the host

The active JVM options were backed up. Competing overrides were checked in the drop-in directory and service unit. The minimum and maximum heap were then raised together from 1 GB to 4 GB.

-Xms1g  →  -Xms4g
-Xmx1g  →  -Xmx4g

Four gigabytes was chosen instead of allocating half of system memory because the monitoring manager, dashboard, shipper, and operating-system page cache shared the same host. The change required one planned service restart.

Validation

Verify the service and the workflow that failed

✓
Heap recognized: the restarted JVM reported a 4096 MB maximum and approximately 27 percent usage at rest.
✓
Cluster recovered: the single-node cluster returned to its expected yellow steady state with active primary shards.
✓
Ingestion resumed: the TCP log session re-established without manual intervention.
✓
Original failure cleared: all seven daily slices of the previously failing query completed successfully.

One operational lesson also came out of the restart: a short red period was normal shard recovery, not proof of a failed change. Documenting the expected recovery state prevented another unnecessary rollback.

Residual risk

The immediate failure was fixed, not hidden

The 540-shard count remains higher than appropriate for this small deployment. The heap increase restored the failed query, but follow-up work must right-size new indices and reduce existing shard count through retention, deletion, or consolidation. A lifecycle policy can automate parts of that work; rollover alone creates another index.

This distinction matters in support work: restoring the customer-impacting workflow does not erase the underlying capacity debt. Both the verified fix and the remaining work are documented.
