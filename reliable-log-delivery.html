Case 02 · Networking and Platform Support

Restoring Reliable Log Delivery

A controlled event appeared on the firewall but not in the monitoring archive. A parallel TCP path was introduced, tested, and cut over while unrelated traffic continued on UDP.

Situation

The sensor logged an event that the destination never received

A controlled network event appeared in the firewall’s local JSON event log but was absent from the central archive. The path used remote syslog over UDP, which provides no delivery acknowledgement and no durable queue.

The goal was not to replace every logging path at once. It was to establish a more reliable route for the highest-value JSON events while preserving the existing path as a rollback option.

Plan

Run the replacement beside the working path

  1. Capture service state, listeners, configuration hashes, and the current network session.
  2. Back up both endpoint configurations before making any change.
  3. Add a source-restricted TCP listener on the receiving platform.
  4. Add a narrowly scoped TCP destination on the firewall.
  5. Validate generated configuration and service syntax before restart.
  6. Send unique markers and fresh events while UDP remained available.
  7. Remove only the target event class from UDP after the parallel test passed.

Rollback remained simple: disable the new destination and listener. The existing UDP route stayed intact until the final cutover was proven.

Implementation

Validate configuration before activation

The receiver was configured with a TCP listener restricted to the firewall’s source address. The firewall’s generated syslog configuration was limited to the event program, the intended facility and severity, and the new destination port.

A missing XML validation utility on the server did not justify skipping the check. The candidate configuration was wrapped and validated with a trusted XML parser from the administrative workstation before installation. The active service’s own test mode was then used before restart.

receiver: TCP listener active and source restricted
sender:   generated configuration syntax valid
session:  TCP connection established
counters: processed = written, dropped = 0, queued = 0

An early marker also exposed a quoting problem that stripped JSON quotation marks. That message still proved transport delivery, but it did not count as structured-data acceptance. A corrected JSON marker was sent and decoded before the change moved forward.

Cutover

Remove duplication without breaking unrelated traffic

Running both transports produced two copies of each matching event. That was expected during the pilot and became the final cutover criterion.

The firewall configuration was changed so the target JSON events used only TCP. Other firewall programs remained on UDP. The generated configuration was checked serially after regeneration, avoiding a stale read during template reload.

Validation

Test every stage, not only the socket

✓
The firewall recorded exactly one fresh test event.
✓
The destination archive contained exactly one structured copy.
✓
The expected classification rule produced exactly one alert.
✓
The TCP destination reported zero dropped and zero queued messages.
✓
Unrelated firewall programs continued sending over the retained UDP path.

Boundary

Reliable delivery is not encrypted delivery

The missing event showed a delivery gap, but did not by itself prove where the UDP path lost it. Direct TCP added transport acknowledgement and eliminated the observed duplicate after cutover; this configuration was not encrypted or durably queued. Those protections require additional transport and architecture work.

What this demonstrates
